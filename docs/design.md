# lighthouse-kit：通用的本地 Lighthouse 扫描、报告与问题文档工具

## 意图

起因：项目里的性能扫描常靠一组零散的本地脚本——构建并起预览和 HTTP/2 代理、逐页跑 Lighthouse、生成每页 HTML 报告和总览、出统计。这类脚本写死了某个仓库的命令、端口、页面和访问限制，只在一台机器上，而且只能出统计，"哪些问题、在哪、怎么改"要人工读 JSON 总结。

要做的是一个与框架无关的工具：Vue、React 或任何能"构建 + 起服务"的前端项目，写一份配置文件，一条命令完成构建 → 起服务 → 扫描 → 分析 → 生成 Markdown 文档 → 浏览器里看总览、每页报告和文档。分析默认不依赖 AI，只靠 Lighthouse JSON 和规则；AI 作为可选的第二层，给出针对代码的具体改法。

## 目标

- 每个项目只需一份配置文件，命令、服务方式、端口、页面、页面准备脚本都在配置里，工具里不写死任何项目的东西。
- 一条命令跑完全流程；每一步也能单独跑（只重扫、只重新分析、只重新出文档、只打开预览）。
- 每页产出与 Chrome DevTools 相同的 Lighthouse 报告（JSON + HTML，含 5 个分类：性能、无障碍、最佳实践、SEO、Agentic Browsing），外加一个总览页。
- 规则分析：从 JSON 归纳问题，按估算收益排序，跨页面合并，把打包文件名对回源码文件，配上内置的修改建议。
- 两种 Markdown 文档，配置里选：开发版（逐条问题、证据、源码位置、改法）和负责人版（分数与核心指标、最差页面、与上次的变化、问题类别分布）。
- 可选 AI 分析：在配置里打开并提供 API Key 时，对排名靠前的问题结合源码给出具体原因和改法，写进开发版。
- 预览：总览页、每页报告、渲染后的文档都是静态 HTML，可直接在浏览器打开，相互可点击跳转；Markdown 原文件同时保留，可提交或分享。
- 历史：完整结果默认只保留最新一轮；另存每轮的小汇总，供负责人版对比和看趋势。
- 每页默认扫 1 次，可配置为多次取中位数。

## 非目标

- 第一版不接 CI，不做性能预算卡点。
- 不测真机，不做真实用户数据（RUM）。
- 第一版只做手机模式；桌面模式以后加（配置项预留）。
- 不做 Claude Code 插件形态（以后可做成调用本工具的薄外壳）。

## 反目标（即使能跑也算失败）

- 没有 AI Key、不开 AI 时，结果残缺或跑不通。
- 需要改动被扫项目的源码，或强制被扫项目加依赖才能用。
- 未经配置打开就把任何源码或报告发到外部服务。
- 新一轮扫描还没成功就删掉了上一轮结果。
- 同一份构建、同样配置下，规则分析的输出不稳定（同样的 JSON 必须得出同样的文档）。

## 约束

- Lighthouse 固定为 13.5.x（与当前 DevTools 一致，且不同版本的审计项不同，结果不可比）；它要求 Node ≥ 22.19。
- 运行环境：macOS 和 Linux；需要本机已装 Chrome/Chromium（路径可配置，也自动探测常见位置和 `CHROME_PATH`）。
- 被扫项目的服务可能需要接口转发、WebSocket（很多项目的预览就是），所以必须支持"用项目自己的命令起服务"，不能只支持静态目录。

## 做法

1. **独立的 Node 命令行工具（选定）。** 单独的目录与 git 仓库 `lighthouse-kit`，命令名 `lhkit`；项目通过 npm 安装或本地 link 使用，配置文件放在项目根目录。纯 Node 实现（扫描、HTML 报告、HTTP/2 代理、统计都在其中），任何前端项目只要有 Node 就能用。规则分析内置，AI 可选。代价：要维护版本，项目要安装或更新它。
2. **助手 skill。** 由 Codex、Claude Code 或其他宿主的当前模型完成分析，无需为 CLI 另配 Key；需要助手会话及文件/终端能力。
3. **把原有脚本改成通用版，按需复制到项目里。** 免安装；但每个项目一份副本，改动要手动同步，很快会不一致。

选 1：最符合"换项目也能用、默认不靠 AI"，AI 只是叠加的一层。

在 CLI 基础上也提供通用 Agent Skills 入口：通过同一套任务导出、回答校验和报告回写复用助手当前模型，见 [多模型与 skill 设计](superpowers/specs/2026-11-26-multi-model-ai-design.md)。

## 已确定的设计

### 位置与形态

- 独立仓库 [wkylin/lighthouse-kit](https://github.com/wkylin/lighthouse-kit)，npm 包名 `lighthouse-kit`（公开发布，也可本地 link），可执行命令 `lhkit`。
- 纯 JavaScript ESM，无构建步骤，用 JSDoc 写类型；配置文件的类型在 `types/index.d.ts`。
- 依赖尽量少：`lighthouse@13.5.x`、`puppeteer-core`（与 Lighthouse 13 配套的大版本）、Markdown 渲染库、自签证书生成；AI 用 Anthropic 官方 SDK，只在打开 AI 时才加载。

### 配置文件

默认在当前工作目录依次查找 `lhkit.config.mjs`、`lhkit.config.js`（`lhkit init` 生成 `.mjs` 模板），通常放在项目根目录。

`run`、`scan` 在没有配置文件时支持 `--url <HTTP/HTTPS 网址>`，将路径、查询参数和 hash 作为完整入口保留；配置中省略 `pages` 也启用自动发现。`src/discover.mjs` 合并 sitemap（含索引）与渲染后的同源链接，默认最多 50 页、链接深度 3 层，每次导航或 sitemap 请求超时 15000 ms；`crawl` 配置及 `--max-pages`、`--max-depth` 可调整范围。入口允许正常重定向，以最终 origin 和根相对路径交给扫描器；后续发现阻止站外导航。sitemap 普通 404 或 SPA 首页回退视为不存在，实际发现错误和目录冲突记入轮次元数据，达到限制或发生错误时将轮次标为部分扫描，避免清理旧的完整结果。

命令行页面优先于配置页面，两种显式列表都跳过发现；配置中存在显式 `pages` 时，既有基础地址及部署前缀拼接语义保持不变。无配置扫描不生成配置文件，默认输出到项目目录的 `.lhkit/`。有配置时仍先读取并校验配置，再应用命令行覆盖；配置存在但有错误时不能静默退回默认值。

所有命令都接受 `--config <目录>`，例如 `lhkit run --config ./apps/web`。参数是配置所在目录，不是配置文件路径；支持绝对路径，或相对于当前工作目录的路径。该目录作为项目根目录，用于执行构建和服务命令、解析配置中的相对路径，并默认将结果写入其中的 `.lhkit/`。`lhkit init --config ./apps/web` 在指定目录生成模板，目录需已存在。

配置示意：

```js
export default {
  build: { command: 'pnpm build -- --sourcemap hidden', env: { VITE_API_MOCK: 'false' } },
  // 三选一：用项目自己的命令起服务；让工具直接托管构建目录（单页应用回退到 index.html，可配接口转发）；
  // 或只写网址，扫一个不由工具启动的服务（已开着的开发服务器、测试环境、线上）
  serve: { command: 'pnpm preview', url: 'http://localhost:4173', readyPath: '/' },
  // serve: { static: 'dist', port: 4173, proxy: { '/api': 'https://api.example.com' } },
  // serve: { url: 'https://www.example.com' },
  https: { enabled: true, port: 4443 },            // 可选：HTTP/2 + 自签证书前置代理，贴近线上
  pages: ['/', '/products' /* … */],
  beforePage: async ({ page }) => {},              // 可选：打开每页前的准备（写 sessionStorage、登录态等）
  runs: 1,                                         // 每页次数，>1 时取中位数那次为代表
  visit: 'first',                                  // 'first' 全新浏览器；'repeat' 先打开一次再扫（模拟回访）
  formFactor: 'mobile',
  categories: ['performance', 'accessibility', 'best-practices', 'seo', 'agentic-browsing'],
  sourceMap: { manifest: 'dist/.vite/manifest.json', maps: 'dist' },
  docs: { audiences: ['dev', 'lead'], lang: 'zh-CN' },
  ai: { enabled: false, provider: 'anthropic', sourceRoot: 'src', maxFindings: 10 },
  outDir: '.lhkit',
  keep: 'latest',                                  // 或保留最近 N 轮
}
```

### 命令

| 命令 | 作用 |
|---|---|
| `lhkit init` | 生成配置模板，按 package.json 里的脚本猜构建和预览命令 |
| `lhkit run [页面…] [--runs N] [--name 目录名]` | 全流程：构建 → 起服务 → 扫描 → 分析 → 文档 → 打开预览 |
| `lhkit build` | 只构建 |
| `lhkit scan [页面…] [--runs N] [--name 目录名]` | 不构建：起服务、扫描（默认全部页面），扫完自动分析和出文档，不打开浏览器 |
| `lhkit analyze [结果目录]` | 对已有结果重新分析、重新生成文档（不重扫） |
| `lhkit preview [结果目录]` | 在默认浏览器打开总览 |
| `lhkit compare <A> <B>` | 两个轮次（按名称或目录）逐页对比分数和指标，输出 Markdown 和 HTML；噪声靠每轮 `runs: N` 的中位数处理 |
| `lhkit ai-export [轮次]` | 导出助手当前会话可分析的任务、证据和允许的源码片段，不调用模型 API |
| `lhkit ai-import <回答文件> [轮次]` | 校验并写回会话建议，重建文档和总览，不重扫、不调用 API |

服务由工具启动的，结束时由工具关闭；端口已被占用时报错说明，不去复用未知进程。

**扫描外部地址**（已与需求方确认纳入第一版）：`serve` 只写 `url`、不写 `command` / `static` 时，工具不构建、不起服务，直接扫该地址；`run` 和 `scan` 都可以用 `--url <地址>` 临时覆盖配置里的目标（例如同一份配置先扫本地、再扫测试环境）。目标地址不在工具里写死。此模式下 HTTPS 前置代理不适用；页面准备脚本 `beforePage` 用于密码门或登录。扫描线上会产生真实请求，文档在概况里注明目标地址。

### 输出目录

```
.lhkit/
  runs/<时间或名称>/
    index.html                 总览：各页分数与指标，链接到报告和文档
    pages/<页面>/run-1/lighthouse.json|html   （runs>1 时有 run-2…）
    pages/<页面>/summary.json   代表那次（中位数）的指标
    analysis.json              规则分析的结构化结果（文档由它生成）
    docs/dev.md  docs/dev.html  docs/lead.md  docs/lead.html
    logs/                      构建、服务、扫描日志
  history/<时间>.json          每轮小汇总（分数与指标），供对比和趋势
```

**轮次与保留**（实现方决定）：
- 每次 `run` 或 `scan` 产生一个新的轮次目录。不带 `--name` 时目录名为时间戳；带 `--name` 的是"命名轮次"。只扫部分页面（命令里列了页面）的轮次标为"部分"。
- `keep: 'latest'` 只清理未命名的完整轮次：新一轮全部页面都扫成功后，才删除上一轮未命名的完整目录。命名轮次和部分轮次从不自动删除，由用户自己删；有页面失败的轮次不触发删除。
- 每轮都写一条 history（记下页面清单和是否部分）。负责人版的"与上一轮对比"和趋势表只使用页面清单相同的完整轮次；部分轮次只出本轮内容。
- 工具在项目的 `.gitignore` 缺少 `.lhkit/` 时给出提示，不自动改。

**历史与可比性**（实现方决定）：每条 history 记录除各页分数与指标外，还记下目标地址（origin）、Lighthouse 版本、`visit`、`formFactor`、`runs`、git 提交号（有则记）、构建目录指纹和时间。负责人版只和"最近一条可比的记录"比较：目标地址、Lighthouse 大版本、`visit`、`formFactor` 都相同才算可比；页面只比两边都有的，新增或缺少的页面单独列出；git 提交和构建不同不影响可比，但写在对比表头里。没有可比记录时，文档写明"无可比的上一轮"，其余部分照常生成。

### 规则分析

1. 读每页 JSON，把未通过的审计和 insight 归一成"发现"：类别、标题、严重度、证据（文件、元素选择器、字节、毫秒）、Lighthouse 估算收益（LCP / TBT / CLS 及字节）。覆盖的类别至少有：主线程长任务与脚本执行、LCP 元素与各阶段耗时、渲染阻塞、请求依赖链、未使用的 JS/CSS、图片、缓存、第三方、非合成动画、布局偏移来源、DOM 规模、旧式 JS、bf-cache、字体、重定向；无障碍、最佳实践、SEO、Agentic Browsing 未通过的项按类归组。
2. 同类问题跨页面合并，标明影响哪些页面；按"估算收益 × 影响页面数"排序。
3. 打包文件对回源码：有 Vite manifest 时按 manifest；否则读 source map 的 `sources`，取占比最大的源文件；都没有时保留打包文件名并在文档注明。webpack / Next 等只要产出 source map 即可。
4. 每类问题配内置的修改建议（规则库，中文为主，预留英文）。
5. 同样的输入必须得出同样的输出；排序有确定的次序。

### AI 分析（可选）

- CLI API 分析在 `ai.enabled` 时运行，支持 Anthropic、OpenAI、DeepSeek 和 OpenAI 兼容服务。默认模型与接口地址可覆盖，Key 从环境变量读取；缺 Key 时提示并使用规则建议，缓存命中无需发请求。
- 只发送 `ai.sourceRoot` 之下、由源码映射命中的文件片段；内置排除名单（`.env*`、密钥与证书文件、`node_modules`、锁文件、构建产物）并可在配置里追加。
- 在配置里打开 AI 即视为同意发送：运行时不逐次确认，一条命令可无人值守跑完。另提供 `--ai-dry-run`：照常分析，列出本会发送的文件和字符数，但不发送、不调用 AI。（已与需求方确认）
- 对排名靠前且有允许源码的最多 `maxFindings` 条发现，把证据和片段交给所选模型，要求返回原因、改法、证据充分程度、源码引用和验证步骤。文件和引用必须匹配实际提供的片段，没有引用只能标为低置信度。规则建议保留在旁边；历史建议可沿用并标注本次未重新核验。
- 源码字符预算、回答 token、超时、有限重试、并发、缓存、语言与额外业务约束均可配置。默认并发 2，按请求、证据和源码内容匹配缓存；API 与 skill 共用源码筛选器及回答校验器。
- `skills/lighthouse-kit/SKILL.md` 定义模型中立的会话流程。`ai-export` 无需 Key 或打开 API；`ai-import` 整批校验轮次、请求 ID、源码是否变化及引用后才写回报告，错误时原文件不变。配置和完整用法见 README 的 AI 分析一节。
- 发送内容在文档末尾列出（哪些文件、多少字符），便于审查。失败或超时回退为规则建议，不影响其余流程。

### 文档

- **开发版 `dev.md`**：本轮概况 → 跨页面问题清单（按优先级：标题、影响、涉及页面、证据表、源码位置、建议、可选的 AI 建议）→ 各页面小节（分数、该页前几项问题、报告链接）。
- **负责人版 `lead.md`**：全站分数与核心指标表、最差的几个页面、与上一轮（history 里最近一条）的升降、问题类别分布、最近几轮的趋势表；不含代码细节。
- 文档自成一体：结论、证据表和建议都写在文档正文里，单独拷走、提交或贴出去仍然完整可读。文中指向每页 `lighthouse.html` 的链接用相对路径，在轮次目录内（预览、编辑器）可点；拷到别处后这些链接失效，文档内容不受影响。（实现方决定）
- 第一版 `history/` 只在本机，不做团队共享。（实现方决定）

### 预览

全部是静态文件，不需要常驻服务：`index.html` 总览（各页分数与指标的表格，加上文档入口），Lighthouse 自带的 HTML 报告（随系统深浅色），文档的 HTML 版本由 Markdown 渲染得到，样式与总览一致。`lhkit preview` 只是用默认浏览器打开总览。

### 多次扫描（实现方决定）

`runs > 1` 时：文档和总览里的分数与指标取各次的中位数；问题证据（审计明细）来自"性能分最接近中位数"的那一次，文档注明证据来自第几次，避免指标和证据互相矛盾。

### 浏览器与 HTTPS

- 无头 Chrome；`visit: 'first'` 时每页全新配置（等同首次访问）；`'repeat'` 时每页一个独立的临时配置：先正常打开一次、再在保留存储的情况下扫描（等同回访，接近在 DevTools 里跑的结果）。（实现方决定）
- `beforePage` 在每次打开页面前都运行（回访模式下预热和正式扫描各一次）。第一版不内置登录流程：需要登录态的项目在 `beforePage` 里自行写入 token 或 cookie。（实现方决定）
- 静态托管模式的接口转发同时支持 HTTP 和 WebSocket。（实现方决定）
- 只支持 macOS 和 Linux，不支持 Windows；规则库第一版只有中文，英文留接口。（实现方决定）
- `https.enabled` 时启动内置 HTTP/2 前置代理（含 WebSocket 转发），自签证书首次自动生成并缓存，Chrome 忽略证书错误。

### 对比新旧构建的流程（实现方决定）

不做替换构建目录这类做法。流程是：切到旧提交 → `lhkit run --name base` → 切回新提交 → `lhkit run --name new` → `lhkit compare base new`。命名轮次不会被自动清理，所以两边结果能同时保留。

### 接入现有项目

- 配置写在项目根目录，结果放 `.lhkit/`。有访问限制（密码门、登录）的项目：构建时用环境变量关掉，或在 `beforePage` 里写入凭据。
- 项目关闭了 source map 时，manifest 里的共享代码块没有源文件路径。lhkit 的构建命令给 Vite 加 `--sourcemap hidden`（只多出 `.map` 文件，JS 里不加引用，Lighthouse 看到的内容不变），不改项目配置。页面级代码块对到它的入口文件（`.vue` / `.tsx`）即可。（实现方决定）
- 先在同一份构建下与原有扫描方式对齐结果（同一 Lighthouse 版本下分数在波动范围内一致），再替换原有脚本。
